# SpeaKO 아키텍처 회고 및 보완책

> 2026-08-22 작성. 시연(08-21)까지의 실제 구조, 실측 수치, 병목, 보완책, 운영 사고와 교훈을
> **다음 프로젝트에서 그대로 참고할 수 있게** 정리한 문서입니다. 수치는 전부 EC2 로그 실측입니다.

## 1. 현재 아키텍처

### 1.1 구성

```
[브라우저] ──HTTPS──▶ [Vercel: React SPA]
                          │  /api/* 리라이트(프록시)
                          ▼
                   [EC2 t3.small 2GB]
                   ├─ Spring Boot :8080  (JWT, MySQL, S3)
                   │      │ http://localhost:8000 (X-API-Key)
                   │      ▼
                   └─ AI 서버(FastAPI, Docker) 127.0.0.1:8000
                          │ SQLite(/app/data), ffmpeg, Kiwi/G2P, 썸네일 워커
                          ├─▶ HCX-005 (대본 생성·감수·상세 피드백)
                          ├─▶ Azure Speech koreacentral (발음 평가, 연속 인식)
                          └─▶ Clova Voice (단어 TTS)
```

| 층 | 역할 | 데이터 |
|---|---|---|
| 프론트 (Vercel) | SPA. API는 상대경로 `/api/*` → `vercel.json` 리라이트로 EC2에 프록시 | 없음 |
| 스프링 (EC2) | 인증·사용자·발표 도메인 소유. AI 서버를 내부 호출 | MySQL: users, presentations, slides, scripts, evaluations, pronunciation_highlights, download_logs / S3: 원본 파일 |
| AI 서버 (EC2, Docker) | 생성·분석·평가·TTS. 외부 AI 3종을 감쌈 | SQLite: projects, slides(source/script), difficult_words, evaluations(words_detail, feedback), 썸네일 PNG |

두 DB는 `presentations.ai_project_id ↔ projects.id`로만 연결된다(스프링이 키를 보관).

### 1.2 주요 흐름과 실측 소요시간

| 흐름 | 경로 | 실측 |
|---|---|---|
| 대본 생성 | 스프링 `POST /presentations` → AI `POST /projects` → `POST /script/full`(202) → 스프링이 3초 간격 폴링 → `saveScripts` → 하이라이팅(`/analysis/words`) → 썸네일 포함 상세 조회 | 텍스트형 18장 33초, 14장 1분 38초~2분 7초, 이미지형은 업로드(비전 OCR)만 87초 |
| 전체 재생성 | 슬라이드·대본 삭제(FK CASCADE로 하이라이트 자동 삭제) → 위와 동일 | 14장 5분 21초, 소규모 57초 |
| 부분 재생성 | `POST /script/partial` 1회 | 6~10초 |
| 커스텀 대본 등록 | `POST /projects`(mode=coaching 또는 script_text) → 즉시 하이라이팅 | 1.3~7초 |
| 발음 평가 | 스프링 `POST /evaluations/record` → AI `POST /evaluation/audio`(ffmpeg→WAV→Azure 연속 인식) → 스프링이 이어서 `POST /evaluation/{id}/feedback`(HCX) | 30~50초 녹음 35~56초, 2분 녹음 2분 35초 |
| 발음 듣기 | `POST /audio/tts/highlight` → AI `POST /tts/word` → MP3 바이트 | 0.2초 |
| 다운로드 | 스프링이 DB에서 대본/하이라이트 텍스트 조립 | 즉시 |

### 1.3 동시성 한도 (실제 값)

| 자원 | 한도 | 초과 시 |
|---|---|---|
| AI 생성 작업 스레드풀 | 4 (`SCRIPT_JOB_CONCURRENCY`) | 대기열 (실패 아님) |
| 스프링 DB 커넥션(Hikari 기본) | 10 | 생성 1건이 폴링 내내 1개 점유 → ~8건 동시 생성부터 대기 |
| Azure Speech | F0 공식 동시 1건 | 실측은 2건 동시도 통과했으나 보장 없음 |
| 오디오 | 20MB / 15분 | 422 + 안내문 |
| Vercel 프록시 타임아웃 | 실측 1분 미만 통과, 2분 35초 끊김 | 프론트는 502/504를 보지만 서버는 완주·저장 |

## 2. 병목 분석 (시연에서 "한 번에 하나만 된다"고 느낀 이유)

| # | 병목 | 근거 | 원인 |
|---|---|---|---|
| B1 | 대본 생성이 느리다 | 14장 2~5분 | 슬라이드를 **한 장씩 순차**로 HCX 호출 + 2차 감수 패스. 14장 = HCX 왕복 14번을 줄 서서 기다림 |
| B2 | 요청이 동기(blocking) | 프론트가 몇 분씩 대기, Vercel 타임아웃 | 스프링 `generatePresentationAndScript`가 `@Transactional` 안에서 AI를 폴링하며 **응답을 붙잡음**. Tomcat 스레드 + DB 커넥션을 작업 내내 점유 |
| B3 | 평가가 녹음 길이에 비례 | 2분 녹음 → 2분 35초 | Azure가 실시간의 약 0.5배 속도로 처리 + 끝난 뒤 HCX 피드백 생성까지 **같은 요청 안에서 직렬** |
| B4 | 중복 요청 | 평가 POST가 2건씩 | 프론트 이중 발송 → Azure 비용·부하 2배 (08-19 오후 수정됨) |
| B5 | 한 박스에 전부 | t3.small 2GB | 스프링·MySQL·AI·ffmpeg·Azure SDK·G2P 동거. 생성 중 여유 메모리 589MB까지 하락 |

"한 작업만 된다"는 하드 제한이 아니라(생성 4병렬·평가 2동시 실증) **B1+B2의 조합으로 한 작업이 화면을 몇 분씩 점유한 체감**이었다.

## 3. 보완책 (효과 대비 난이도 순)

| 순위 | 보완책 | 어디 | 난이도 | 기대 효과 |
|---|---|---|---|---|
| 1 | **슬라이드 병렬 생성** — 장별 독립 호출이므로 4~6장씩 동시에 HCX 호출 | AI 서버 `full_generation` | 반나절 | 14장 5분 → 1분 안쪽. 품질 동일. **시연 전에 했어야 할 한 가지** |
| 2 | **스프링도 접수→폴링(202 + job id)** — AI는 이미 job API(`step_label` 포함) | 스프링 컨트롤러·서비스, 프론트 폴링 | 1~2일 | 화면이 안 멈춤, DB 커넥션 점유 해소, Vercel 타임아웃 문제 소멸, 진행 단계 표시 가능 |
| 3 | **상세 피드백을 평가 응답에서 분리** — 점수 즉시 반환, 피드백은 백그라운드/온디맨드(AI는 이미 캐시 지원) | 스프링 `evaluateVoice` | 시간 단위 | 평가 체감 5~10초 단축 |
| 4 | **완료된 장부터 표시** — 폴링 응답에 완성 슬라이드 동봉 | AI job 응답 + 프론트 | 하루 | 총시간 같아도 체감 대기 10초대 |
| 5 | **인프라 분리·증설** — t3.medium+, uvicorn 워커 2~4, MySQL 분리, Azure S0 | 인프라 | 비용 | 동시 사용자 수 자체 증가 |
| 6 | **긴 녹음 분할 병렬 평가** — 슬라이드 단위로 쪼개 Azure 동시 호출 후 합산 | AI 서버 | 2~3일 | 2분 녹음 30초대. 점수 합산 로직 필요 |
| 7 | 타임아웃 예산표 — "프론트 대기 < 프록시 타임아웃 < 서버 작업 상한"을 설계 시점에 적음 | 팀 규칙 | 0 | 08-19의 502 혼선 예방 |

## 4. 운영 사고 기록과 교훈 (08-17 ~ 08-19)

| 사고 | 증상 | 원인 | 교훈 |
|---|---|---|---|
| `AI_BASE_URL` 끝 슬래시 (하루 3회) | 스프링→AI 전부 404, 기동 로그는 정상 | 수동 `export`로 재시작하며 `http://localhost:8000/` 입력 → `//api/...` | **재시작은 스크립트 한 줄로만**(`start-spring.sh`). 환경변수는 사람이 치지 않게 |
| Azure 구독 비활성 | 평가가 전부 "음성을 인식할 수 없습니다" | 무료 크레딧 만료로 구독이 읽기 전용 → 키 401. SDK 연속 인식 모드는 인증 실패를 **이벤트 없이 조용히 종료** → 서버가 무음으로 오인 | 외부 키는 **만료일·구독 상태를 달력에**. 인증 실패와 무음은 다른 메시지로 구분(단발 인식 프로브로 판별 가능) |
| 재활성화 후 간헐 실패 | 연속 인식만 30분간 오락가락 | 구독 재활성화 전파 지연 | 복구 직후엔 "2연속 성공"을 안정화 판정 기준으로 |
| Mixed Content | HTTPS 프론트가 HTTP IP 호출 차단 | 백엔드에 HTTPS 없음 | 프론트는 **상대경로 + 리라이트 프록시**(08-19 적용). 대신 프록시 타임아웃 예산이 생김 |
| 테스트 중 배포 | 재생성 1건 500 | 폴링 중 AI 컨테이너 교체 → Connection reset | **연동 테스트 중엔 배포 금지**, 1분간 생성·평가 0건 확인 후 교체 |
| 문서와 배포본 불일치 | 스프링 수정 안내가 실제 코드와 안 맞음 | 담당자 소스 스냅샷 기준으로 작성 | 스프링 안내는 **배포 JAR을 디컴파일(CFR)해 검증**한 뒤 작성 |
| 다운로드 500 ×2 | enum 불일치 → FK 실패 | 스프링 enum에 `txt` 추가됐는데 DB는 `docx/pdf`; 로그 `user_id` 1 하드코딩인데 users에 1번 없음 | 스키마 변경은 **DB ALTER를 배포보다 먼저**, 하드코딩 id 금지 |
| 완성도 부풀림 | 대본 일부만 읽었는데 90점 | Azure 세그먼트별 완성도는 안 읽은 뒷부분을 계산에서 누락 | 완성도를 **대본 전체 단어 수 기준으로 직접 계산**하고 종합점수 재산출(08-19 배포) |
| 평가 `presentationId` 누락 | 즉시 500 (0.2초) | 한 화면만 파라미터 누락 | 같은 API를 부르는 화면이 여럿이면 **호출 모듈을 하나로** |

## 5. 다음 프로젝트 체크리스트

**설계**
- [ ] 외부 AI 호출은 처음부터 **접수(202)→폴링** 구조. 동기 응답으로 기다리게 하지 않는다
- [ ] 독립 단위(슬라이드 등)는 **기본 병렬**, 동시 상한은 환경변수로
- [ ] 타임아웃 예산표: 프론트 대기 < 프록시 < 서버 작업 상한. 표로 적어 공유
- [ ] 긴 작업은 진행 단계(step)를 응답에 싣고 화면에 표시
- [ ] 에러 메시지는 원인별로 구분(인증 실패·무음·타임아웃이 같은 문구면 진단이 30분 돌아간다)

**운영**
- [ ] 재시작·배포는 스크립트 한 줄. 환경변수는 파일에서 읽고 주입 결과를 출력
- [ ] 외부 구독(Azure·HCX·Clova) 만료일과 상태를 달력·문서에 기록, 시연 3일 전 점검
- [ ] 연동 테스트 중 배포 금지. 교체 전 "1분간 진행 작업 0건" 확인
- [ ] 배포 전 JAR·이미지·DB 덤프 백업(`~/backups/날짜/`) + 롤백 한 줄 명령 준비
- [ ] 로그에서 호출 출처 구분(도커 호스트 `172.17.0.1` = 스프링, `127.0.0.1` = 내부 테스트)
- [ ] 프론트 중복 발송 방지(요청 중 버튼 비활성화) — 유료 API는 비용이 바로 2배

**협업**
- [ ] 다른 팀 코드에 대한 안내는 **배포본을 직접 확인**한 뒤 "지금 코드 → 바꾼 코드" 형식으로
- [ ] 키는 채팅으로 주고받지 않고 서버 `.env`에 직접, 해시로만 대조
- [ ] 시연 대본처럼 라이브로 오래 걸리는 건 미리 돌려두고, 라이브는 10초 안쪽 기능으로
